# AROVA — Full-Stack Development Master Specification

Build AROVA, a functional, offline-first, voice-assisted healthcare documentation web application for ASHA workers.

This project is being developed for a 24-hour hackathon. Prioritize a functional end-to-end workflow, reliable data persistence, correctness, a polished user interface, and working integrations over unnecessary features.

The application must be a working full-stack web app, not merely a UI prototype.

---

# 1. PRODUCT DEFINITION

AROVA is a healthcare documentation and patient-record management application designed for ASHA workers.

Its purpose is to:

- Capture patient visit information using voice.
- Support multiple languages.
- Convert voice recordings into transcripts.
- Extract information into structured patient visit reports.
- Identify missing information.
- Allow the ASHA worker to verify and correct information.
- Read reports and captured information aloud.
- Maintain patient profiles and visit histories.
- Manage visit reminders, follow-ups, and tasks.
- Work offline.
- Persist records locally.
- Synchronize data incrementally when internet connectivity becomes available.
- Recognize community health patterns from available records.
- Display rule-based danger-level flags without diagnosing patients.

AROVA is strictly a healthcare documentation and reporting application.

## Explicitly prohibited functionality

AROVA must NOT:

- Diagnose diseases.
- Generate medical diagnoses.
- Provide medical suggestions.
- Recommend treatment.
- Prescribe medication.
- Invent patient information.
- Automatically convert uncertain information into confirmed information.
- Replace healthcare professionals.

It is a report-making and record-management application.

Danger-level prediction is strictly a rule-based flagging feature using predefined medical rules. It must not function as diagnosis, treatment advice, or a medical recommendation engine.

## Recording

- Save locally

- Recording state

## AUDIO COMPRESSION

The application must compress recorded audio to reduce storage and network usage.

### Strict requirement:

**Compress recordings. Do not slice, split, chunk, or segment recordings into multiple audio pieces.**

The recording must remain one logical recording.

Do not implement:

- Audio chunk splitting
- Chunk-by-chunk transcription workflows
- Automatic segmentation into multiple files
- Recording slices

Compression may reduce bitrate, file size, or use an efficient audio codec, provided the recording remains one complete audio file.

Preserve the full recording and its continuity.

The compressed audio file should be stored locally and uploaded as a single logical recording when required by the selected API integration.

If the API imposes a limitation, document it and choose the appropriate supported upload or WebSocket method without implementing recording slicing.

## Architecture Principles

1. Local data is immediately persisted.
2. Network availability must not determine whether a visit can be saved.
3. Processing is deferred when necessary.
4. Synchronization is incremental.
5. Server requests must be idempotent.
6. Background processing must be persistent.
7. Every record must have a unique identifier.
8. Every processing operation must have a visible status.
9. Failed operations must be recoverable.
10. Never discard a patient record silently.

# 7. REQUIRED PERSISTENT QUEUE

Implement a persistent queue.

The queue must survive:

- Browser refresh
- Tab closure
- Application restart
- Temporary internet loss
- Failed processing
- Failed synchronization

Do not keep the queue only in RAM.

Queue entries must be stored in IndexedDB.

Each queue entry should contain:

- Unique queue ID
- Associated patient ID
- Associated visit ID
- Operation type
- Payload/reference
- Creation timestamp
- Last attempted timestamp
- Retry count
- Status
- Error information
- Next scheduled retry time
- Idempotency key

## Queue Statuses

Use statuses such as:

- Pending
- Processing
- Waiting for connection
- Retry scheduled
- Failed
- Completed

## Deferred Processing

When the internet or required API is unavailable:

- Preserve the queued operation.
- Mark it as deferred.
- Wait until processing is possible.
- Resume processing when connectivity returns.

Do not discard queued jobs.

---

# 8. RETRY LOGIC

Implement retry logic for temporary failures.

Examples:

- Network failure
- API timeout
- Server error
- Transcription failure
- Temporary AI failure
- Synchronization failure

Use exponential backoff.

Example strategy:

```text
Attempt 1 → Immediate
Attempt 2 → 2 seconds
Attempt 3 → 4 seconds
Attempt 4 → 8 seconds
Attempt 5 → 16 seconds
```

Use reasonable maximum retry limits and maximum delays.

Add jitter to prevent repeated synchronized retries.

Permanent errors should not be endlessly retried.

The user must be able to manually retry failed jobs.

---

# 9. IDEMPOTENCY

Every operation that can be retried must have a unique idempotency key.

Examples:

- Creating a patient
- Creating a visit
- Uploading a recording
- Creating a report
- Synchronizing data

If the same request is received multiple times, it must not create duplicate records.

The backend must validate and recognize duplicate idempotency keys.

---

# 10. BACKGROUND EXECUTION

Implement background work scheduling where supported.

Possible tasks:

- Pending audio processing
- Deferred transcription
- AI extraction
- Synchronization
- Report generation
- Pending queue processing

Use:

- Persistent local queue
- Background processing
- Background Sync API where supported
- Service Worker where appropriate
- App-level processing when the application is active

Browser background capabilities are limited.

Do not falsely claim that processing can continue indefinitely when the browser is completely closed.

If background execution is unavailable, resume automatically when the application opens or becomes active.

---

# 11. RESUME SUPPORT

Every operation must be recoverable.

If:

- The application crashes
- The browser closes
- Internet disappears
- A request times out
- AI processing fails

The operation must retain enough state to resume.

Use persistent state tracking.

Do not restart the entire workflow unnecessarily.

Resume from the last successfully completed stage where possible.

Example:

```text
Recording saved
      ↓
Compression completed
      ↓
Transcription pending
      ↓
Transcription completed
      ↓
Extraction pending
      ↓
Extraction completed
      ↓
Verification pending
```

Each stage must have a persisted state.

# 13. SCHEMA VALIDATION AND MEDICAL RULES

Every AI extraction must be validated.

Use structured schemas.

Use Zod or an equivalent schema-validation library.

Validate:

- Data types
- Required fields
- Dates
- Numerical values
- Field consistency
- Allowed values
- Missing information

Use medical rules only for:

- Required-field validation
- Consistency checking
- Predefined danger-level flagging
- Identifying missing information

Medical rules must not generate diagnoses or treatment suggestions.

AI output must not bypass validation.

Invalid output must be flagged and reviewed.

# 14. DANGER-LEVEL PREDICTION

Implement a danger-level prediction/flagging feature.

This feature must be rule-based using clearly defined predefined criteria.

It is not a diagnosis.

It does not provide treatment advice.

It should only flag information for review according to predefined rules.

Possible output:

- No predefined danger flag detected
- Flag detected
- Information incomplete
- Manual review required

Every flag must show:

- The specific recorded information triggering the flag
- The applicable rule
- The reason the flag was triggered
- Whether the information is verified

Never invent clinical thresholds.

Do not implement medical rules from guesses.

Use documented, explicitly configured rules.

If a rule cannot be safely configured, make the feature clearly indicate that rules are pending configuration.

# 22. INCREMENTAL SYNCHRONIZATION

The internet is used for incremental synchronization only.

Do not make the application dependent on continuous internet access.

When connectivity returns:

1. Detect connectivity.
2. Identify changed local records.
3. Identify pending operations.
4. Send only necessary changes.
5. Use idempotency keys.
6. Handle synchronization errors.
7. Retry appropriately.
8. Update sync metadata.
9. Preserve records if synchronization fails.

Do not repeatedly upload unchanged records.

Implement incremental synchronization.

## Conflict Handling

If local and remote data conflict:

- Do not silently overwrite data.
- Detect the conflict.
- Preserve the local version.
- Preserve the remote version where necessary.
- Provide a conflict-resolution workflow.
